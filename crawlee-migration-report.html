1. Behavior changes vs. the old crawler

Improved

1a. List handler is faster but semantically equivalent

The old code's per-card N+1 query pattern was replaced with one batched inArray() lookup, batched inserts, and a single addRequests() call.

I traced every branch (new, price-changed, resurrected, unchanged) and confirmed the detail-enqueue rule from the old code (!detailCrawled) is preserved exactly in the new code.

Net: fewer round-trips, same outcome.

Improved

1b. New inserts now use onConflictDoNothing()

The old code would crash on a unique-constraint violation when two crawl runs raced on the same adId. The new code silently skips the duplicate.

The downside is that if the conflicting card has fresh data (e.g. updated price), the in-memory card values are dropped on conflict — the existing row is not updated, and only the DETAIL handler later refreshes it.

You don't run concurrent full crawls, so this is theoretical, but worth knowing.

Worth watching

1c. Multi-category crawls now run sequentially, one Crawlee instance per category

Old
const requests = categories.map(...);
await crawler.run(requests);
// one queue, one session pool
New
for (const cat of categories) {
  const c = createCrawler(...);
  await c.run([req(cat)]);
}

Implications:

  • Throughput is roughly the same — maxConcurrency: 3 was already the cap.
  • Session pool is reset between categories. The old single pool warmed up across all categories; the new approach starts cold each time. For a non-aggressive site like Encuentra24 this is unlikely to cause blocks, but it is a change.
  • A few seconds of lost overlap at category boundaries. Negligible at full-crawl scale.
  • betweenCategoryDelaySecs: 5 was added to config but is never read anywhere in code. Either dead or intended for future use.
Worth watching

1d. config.crawler.listingsPerPage changed from 30 to 20

Used only at src/crawler/router.ts:351 as a fallback for max-page estimation when the flight payload lacks metadata.totalPages but has metadata.total.

The primary pagination path comes from metadata.totalPages directly (src/crawler/extractors/list-page.ts:234), so this change is mostly harmless — a wrong value just causes a few extra empty pages that the LIST handler short-circuits with "no listings found."

Verify the actual page size empirically; if E24 still serves 30, you'll just over-paginate slightly on edge cases.

Preserved

1e. Full-crawl removed-listing detection still works

The safety check (activeCount >= 1000 && seen < 50% aborts) and the crawl_seen_listings-based marking logic are unchanged. tracksSeenListings is still computed once and propagated through every per-category crawler in the sequential loop.

The new crawlDetails: false mode does not break removal detection — seen-tracking happens in the LIST handler, independent of detail crawling.

This is the most important reliability invariant and it survives.

Fixed

1f. Stats counting is now correct

The old getCrawlStats() did SELECT COUNT(*) FROM listings and stored that as listingsFound for every run, which was wildly wrong (it returned the size of the entire table, not what this run found).

The new code uses runtime counters from the metrics module, with a special fallback to crawl_seen_listings for full crawls. This is a correctness fix, not a regression.

Heads up: historic crawl_runs.listings_found rows from before this change are still meaningless — be aware when comparing trend lines across the migration boundary.
Fixed

1g. Log levels actually work now

Old code: --log-level error was silently treated as info. The new toLogLevel() maps debug/info/warn/error correctly.

Just flagging in case you scripted around the old quirk.

2. Higher-risk concerns

Higher risk

2a. The two migration folders are a footgun

drizzle/ (new) is an auto-generated fresh-start snapshot that does CREATE TABLE (not IF NOT EXISTS) for every crawler table. migrations/ (existing) holds the four manually-written incremental SQL files that have been applied to production by hand.

src/db/migrate.ts points to ./drizzle (and was already pointing there at HEAD — not changed in this branch). So:

  • If anyone runs npm run db:migrate against production, every CREATE TABLE will fail because tables already exist. PostgreSQL transactions roll back cleanly — no data loss — but the migrator's tracking table (__drizzle_migrations) is left in an inconsistent state, breaking future drizzle-managed migrations.
  • drizzle/0000_wooden_moon_knight.sql does not include the web-only tables notification_digest_runs, notification_digest_items, notification_recipients, notification_deliveries. A fresh local DB initialized from ./drizzle will miss them; the WhatsApp digest endpoints will 500.
  • The CLAUDE.md rule "NEVER use db:push against production — use migrations only" is the right call, but db:migrate itself is now also unsafe-to-run against prod.
Suggested mitigation before merging: either delete drizzle/ and keep using manual SQL files, or add IF NOT EXISTS to every CREATE in 0000_wooden_moon_knight.sql so it's idempotent for production. At minimum, document this in CLAUDE.md.
Higher risk

2b. Apify Actor adds a brand-new failure surface

src/actor/encuentra24.ts is the new entry point for Crawlee Cloud / Apify runs. It's well-structured (zod-validated input, OUTPUT key write, closeDb() in finally), but:

  • It uses top-level await with await Actor.init() and writes via Actor.pushData and Actor.setValue. If Actor.init() ever throws (token issues, env mismatch), you skip the catch handler entirely.
  • The whole flow assumes apify is actually installed at runtime. The Dockerfile copies node_modules from the build stage after npm prune --omit=dev, and apify is a regular dep, so that should be fine — but worth a smoke test of the built image: docker run … node dist/actor/encuentra24.js against the local DB.
  • Sessions are not persistent (persistCrawlerStorage: false for actor runs), so any crash mid-run loses all in-flight URLs. Apify won't retry partial runs; you'd need to re-run the whole thing. Same as before for the GCE VM cron, but it's worth knowing.
Worth watching

2c. Dataset sync floods the Apify dataset on full crawls

With syncDataset: true (the actor default), a full crawl pushes ~45,000 listing.card.inserted events plus per-detail events to the Apify dataset.

That's roughly 1,500 batched Actor.pushData() calls of ~30 events each, plus 45,000 detail events done one-at-a-time (because the DETAIL handler pushes per request) — see src/crawler/router.ts:582-608.

If you hit any rate limit it just logs a warning and continues (src/crawler/dataset-sync.ts:62-67), so the dataset will have gaps. PostgreSQL is the source of truth, so data integrity is fine — but if you rely on the dataset for monitoring, gaps will show.

Suggestion: consider batching detail events too, or making syncDataset: false the default for full mode.
Worth watching

2d. Per-detail dataset event includes the entire updates object

At src/crawler/router.ts:599:

listing: { ..., ...updates, rawJsonLd: undefined, ... }

updates may include images (an array), amenities, description (long text). The compactValue helper truncates strings >1000 chars, but it does not truncate large arrays or descend into nested objects.

A listing with 30 image URLs sends a big payload per detail. Memory is fine; ingress cost on Apify is what to watch.

Worth watching

2e. The agents/route.ts change is unrelated and buried in this branch

The diff in web/src/app/api/agents/route.ts (INNER JOIN → LEFT JOIN, swapping the location filter from pa.primary_location to l.location, and the location dropdown query) is a separate logic fix in the agents API. It's not part of the crawler migration.

Mixed in here it's hard to review carefully — recommend splitting it into its own commit/PR.

Verify the LEFT JOIN isn't producing duplicate agents now (since primary_areas may have multiple rows per seller in some configurations) before shipping.

3. Smaller findings

Note

3a. CLI --skip-details wired correctly

src/cli/commands/crawl.ts correctly wires the new --skip-details flag. Old cron scripts (scripts/vm-crawl.sh) use --full only — they keep working as before. No CLI regression.

Note

3b. migrate.ts uses top-level await + process.exitCode

This is cleaner but means migration failures no longer exit immediately — they wait for closeDb() to finish. Generally fine; just note that any hung pg connection could delay the process.

Note

3c. Per-instance Configuration is correct, but watch ./storage in multi-category mode

createCrawler accepts a Configuration per instance (good), but you could leak ./storage pollution across category boundaries if you ever set persistCrawlerStorage: true in multi-category mode — cleanupStorage only runs once at the start of runCrawl().

With the default false, this is moot.

Note

3d. incrementCrawlMetric() silently no-ops if the run isn't tracked

See src/crawler/metrics.ts:36-37. If a request fails after finishCrawlMetrics() (e.g., a late retry on shutdown), its error counter is dropped.

Edge-case logging gap, not a correctness bug.

Note

3e. crawl_runs row on failure only sets status + errors

Other counters stay at their defaults (0). Same behavior as the old code, but worth knowing for post-mortems on partial crawls.

Note

3f. probe-site and ph commands are read-only and well-isolated

Low risk. PH (propiedad horizontal) detection is a separate analysis tool unrelated to ingestion.

Note

3g. Crawler timeouts unchanged

requestHandlerTimeoutSecs: 60 and navigationTimeoutSecs: 30 are unchanged — same as before.

4. What to verify before cutting over

  1. Run the actor against a fresh local DB twice

    Run an incremental, then a small full crawl, and diff the resulting listings row counts and crawl_runs.listings_found against a known-good production-derived snapshot for the same category.

  2. Decide on the migration story

    Either delete drizzle/, or make it idempotent (CREATE TABLE IF NOT EXISTS), or document loudly that db:migrate must never run on prod. This is the single highest-risk item in the branch.

  3. Test the actor's failure path

    Trip Actor.init() (e.g., bad token) and confirm closeDb() still gets called and the process exits cleanly. The top-level await can bypass the catch on init failure.

  4. Smoke the Docker image

    Run docker build then run the image with E24_ACTOR_INPUT_JSON='{"mode":"incremental","maxPages":1}' against a disposable DB. The Dockerfile's npm prune --omit=dev is the most likely place a missing runtime dep would surface.

  5. Confirm the web/src/app/api/agents/route.ts change is intentional and correct

    It's a separate concern that snuck into this branch. Validate that the LEFT JOIN doesn't produce duplicate agent rows.
